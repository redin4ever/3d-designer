# Drift — decided vs built

## Method

Read `docs/decisions/gate-A.md` (48 decisions), all 11 `docs/adr/*.md`, and
`docs/ASSUMPTIONS.md` (A-001..A-010) as authority. Walked every decision and ADR against
`src/`, `frontend/`, `docs/`, reading real source (never test files as proof of behaviour)
and confirming with `python -c` against the live `app.build_app()` where a claim was
checkable at runtime (Python at `%LOCALAPPDATA%\Programs\Python\Python313\python.exe`,
`prefer_blender=False` — no Blender needed for wiring/registry questions). Did not re-derive
the four leads supplied (export_scene KeyError, dual registries, measure/detail zero specs,
AcceptanceQuery unreached) but used each as a starting point and traced the mechanism behind
it. Cross-read `docs/research/review-1/debt.md`, `behaviour.md`, `experience.md` (sibling
reviews already in the tree) to avoid restating their findings; cited only where this review
adds a new mechanism or a new citation they didn't carry. A recurring pattern: several real
gaps are honestly documented in module `CLAUDE.md`/docstrings but never reconciled into
`docs/ASSUMPTIONS.md` or an ADR as Rule 1/3 require — these are marked **undocumented** below
because that is the standard the rules themselves set, not because no one, anywhere, wrote a
comment about it.

## Summary (matches: 36, deliberate drift: 2, undocumented drift: 11, not built: 1 — of 48 gate decisions; ADR-level drift folded into the items below)

## Undocumented drift

**1. The entire browser control surface (5.1, 5.3, 5.4, 3.1, ADR-011) is built and real, but never reachable in a running server.** `src/viewer/server.py:66-88` (`serve()`) is the function that actually opens `websockets.serve(...)`; it is exported (`src/viewer/__init__.py:17`) but OBSERVED nowhere imported outside `src/viewer/` and its own tests. `src/app/__init__.py:134-140`'s `attach_viewer` path only constructs `ViewerBridge` and calls `.attach()` (`src/viewer/bridge.py:42-47`), which subscribes to scene events in-process — it never starts a socket. `src/forge3d_cli.py:79-104` (`serve`, the actual CLI entry point for `forge3d serve --stdio`/`--http`) never touches `viewer` at all. Confirmed live: `grep` for `server.serve(` / `websockets.serve(` outside `src/viewer/` returns nothing. Separately, MCP itself carries no pause/rollback/redirect/cadence tool by design (`src/mcp_server/registry.py:66-76`'s `_sources()` — only `ops`, `export`, optional geometry modules, `raw`) — so an MCP-connected agent has no path to any of Gate A 3.1/5.4 either. Net effect: cadence-from-a-settings-menu, the live 3D view, the action log, and pause/rollback/redirect all exist as real, tested code (`frontend/src/controls.js:43-134`, `src/viewer/client.py:100-131`, `src/scene/history.py:26-54`) with **no live path from a running `forge3d serve` to a browser at all.**

**2. Phase promotion checks nothing about the geometry — it checks that any operation happened.** `src/orchestration/phases.py:1-7`'s own module docstring states "a phase only hands off when its acceptance queries pass against live geometry" — but `can_promote()` (`phases.py:34-58`) computes `passed = len(produced_this_phase) > 0`: literally "did this phase record at least one non-promotion operation," never a real `contracts.AcceptanceQuery`. This is the mechanism behind the already-known lead that `AcceptanceQuery`/`measure.evaluate()` has zero non-test call sites. `src/orchestration/CLAUDE.md` documents this as a known implementation choice "filed in this task's contractRequests/assumptions output" — but `docs/ASSUMPTIONS.md` (A-001..A-010) contains no entry about it, and `.pipeline/contract-requests.json` has no entry naming `can_promote` either. ADR-005 ("definition-of-done is a re-run measurement, not a claim") and ADR-007 ("a phase hands off when its acceptance queries pass... never when an agent says it is finished") are both directly contradicted by what ships, with no ADR superseding either.

**3. `export_scene` and `check_export_budget` are registered MCP tools with no working execution path.** Live-verified: `dispatch("export_scene", {...}, role=EXPORT, orchestrator=app.orchestrator, lease=<real lease>)` raises `KeyError: "unknown operation kind 'export_scene'; known kinds: add_floor, ... unwrap_uvs, weld_duplicates"` — `export_scene` is not in that list. `src/mcp_server/dispatch.py:89-100`: a mutating tool with `handler=None` (every `ToolSpec` in the codebase, including export's) gets wrapped into a `contracts.Operation` and run through `orchestrator.perform`, which needs `op.kind` in `app.handlers` (`src/app/handlers.py`) — but `export_scene`'s real implementation is a plain function taking an engine directly (`src/export/writer.py:67`, confirmed called that way in `src/app/app_test.py:218`), never registered as an operation-kind handler. `src/app/app_test.py:66` — the exact test built to catch "a tool an agent can see but nothing can execute" — carves out `{"check_export_budget", "export_scene"}` from its own assertion with no comment explaining why. This means the primary "drops into a game engine" path (1.2) is unreachable through the one interface (MCP) the product ships.

**4. The "many look and propose" reader role has zero tools; so does the detail-phase role.** `contracts.ToolRole` (`src/contracts/operations.py:307-341`) defines `INSPECT` as "Read-only. Any number of these may run concurrently (ADR-007)" and `DETAIL` as its own role — but OBSERVED, no real `ToolSpec` anywhere assigns either. `src/mcp_server/registry.py:35-41`'s `_load_optional` silently returns `()` for `measure`/`detail` (no `*_SPECS` constant exists in either module), confirmed by `src/mcp_server/registry_test.py`'s own comment: "DETAIL and INSPECT are legitimately empty today." Gate A 10.1 ("many look and propose, one applies") has no usable reader path in the shipped registry — only the one writer role is populated. Separately: `src/orchestration/_tool_registry.py` (`TOOLS_BY_ROLE`, fictional tool names, `_EMPTY_SCHEMA` throughout) is served by `Orchestrator.tools_for()` (`src/orchestration/phases.py:127-145`) and is confirmed by grep to be called from nowhere in `src/app/` — a second, disconnected registry sits beside the real one with nothing checking they agree.

**5. Saving and reloading a scene silently drops every constraint, joinery intent and acceptance query on every operation.** `src/scene/persistence.py:67-92` (`_operation_to_dict`/`_operation_from_dict`) serialises only `op_id, kind, params, phase, author, target_objects, opaque, produced_objects, status`. `contracts.Operation` (`src/contracts/operations.py:95-139`) also carries `placements` (the `ConstraintSet` — the entire point of ADR-004/6.1's "constraints stay live"), `joinery`, `acceptance`, `asset_class`, `proposal_id` — none round-trip. `src/scene/CLAUDE.md` calls this "a known, documented gap" and explicitly defers it ("no test in this package exercises an operation carrying any of the three"). ADR-002's stated payoff — "move the stair, and the railing that was constrained to its outer edge follows" — does not survive a save/load cycle for that reason: reload a saved scene and the railing's constraint to the stair is gone, only its frozen `params` remain.

**6. Gate A 4.2 ("what rule it broke") is true for some failures and false for others.** `src/app/handlers.py:139-162` (`adapt`) wraps every plain operation function and catches exactly `TypeError` (→ `error_rule="operation.bad_parameters"`); any other exception is not caught here. OBSERVED: `src/contracts/geometry.py:89,141,198,207,270-303`, `src/align/_geom.py`, `src/constraints/_orientation.py`, `src/constraints/_position.py`, `src/ops/_geom.py`, `src/uv/unwrap.py`, `src/spatial/index.py` all raise bare `ValueError`s for degenerate geometry (zero-length vectors, zero quaternions, empty point sets) with no `error_rule` attached — a railing on a genuinely degenerate path would surface a raw Python traceback to the agent, not a named rule. Only failures that a function itself catches and returns as an `OperationResult`-shaped object get a rule. The user specifically flagged this field as something they'd reuse for game-design work (gate-A.md:54); it is not reliable yet.

**7. `add_railing` supplies exactly the real-world dimensions Gate A 6.4 said the tool never would.** `src/ops/railing.py:72-74`: `post_w, post_d = params.get("post_size", (0.05, 0.05))`, `bal_w, bal_d = params.get("baluster_size", (0.03, 0.03))`, `rail_w, rail_d = params.get("rail_size", (0.05, 0.05))` — these three cross-sections are optional in the tool schema (`src/ops/registry.py`, not in `required`) and fall back to hardcoded 5cm/3cm defaults when an agent omits them. Small in scope (three of many railing parameters), but it is precisely the pattern 6.4 ruled out: a built-in default standing in for a dimension the agent was supposed to supply.

**8. `docs/HANDOVER.md` does not exist.** A-004 promises thin areas — named explicitly as rigging and organic sculpting — "go to `docs/HANDOVER.md` with an honest assessment rather than being silently dropped." `find` over the whole repo for any handover file returns nothing. Coverage for rigging/organic is not merely thin, it is zero: repo-wide grep for `armature|rigging|bone|weight.?paint|sculpt|multires|organic` (excluding docs) returns no implementation hits at all. A-004's own commitment to document that honestly was never carried out.

## Deliberate drift (with where the reason is recorded)

- **ADR-008 named a static three.js frontend; what shipped is a hand-written Canvas2D renderer.** `frontend/src/scene-renderer.js:1` states "no three.js" directly; `frontend/README.md:52-68` ("Why viewport.js has no three.js") records the reason: three.js isn't installed and there is no network access to fetch it in this environment. The renderer is real and functioning (perspective projection, quaternion orbit, `requestAnimationFrame` loop), so Gate A 5.1/5.3 ("live 3D view") are still met — only ADR-008's specific technology choice drifted, and no ADR-012 supersedes ADR-008 to make the substitution official.
- **The real MCP SDK server path (`serve_stdio`/`serve_http` against an actual `mcp.server.Server`) is unverified by design, not by oversight.** `src/mcp_server/CLAUDE.md`: "The SDK is not installed in this environment... Every test that can run without the SDK does; the two that would need it do not exist, rather than being written against a guess and silently passing for the wrong reason." (`docs/research/review-1/debt.md` separately found the SDK actually *is* importable in this environment and flagged the claim as stale — cited there, not repeated here.)

## Decisions for the user

- **[Browser control surface]** — The live 3D view, action log, cadence menu, pause/rollback/redirect are all built but the WebSocket server that would let a browser reach a running session is never started. Wire `viewer.serve()` into `forge3d serve` so it starts automatically, or keep it manual but say so loudly in the CLI's own output? (1) Auto-start alongside MCP serve (Recommended) — matches what Gate A 5.1 asked for with zero extra steps. (2) Auto-start only behind a `--viewer` flag — safer default, but the browser experience the user chose becomes opt-in. (3) Leave as-is, document it as a manual second command. Impact: high. Evidence: `src/forge3d_cli.py:79-104`, `src/viewer/server.py:66-88`.

- **[Phase promotion has no real quality gate]** — `can_promote()` currently passes once any operation exists in the phase, not once the phase's actual acceptance criteria (manifold, clipping, budget) are met. (1) Wire `can_promote` to real per-phase `AcceptanceQuery` objects against `measure` (Recommended) — this is what ADR-005/007 describe and what makes "fully autonomous, never stop" (4.4) safe to trust. (2) Keep the current placeholder but rename it honestly and document the gap in `docs/ASSUMPTIONS.md`. (3) Leave as-is, undocumented. Impact: high. Evidence: `src/orchestration/phases.py:34-58`.

- **[Export is unreachable through the shipped interface]** — `export_scene`/`check_export_budget` are visible MCP tools that raise `KeyError` when actually called. (1) Give `export_scene`/`check_export_budget` real `ToolSpec.handler` callables that call `export.export_scene`/`export.check_budget` directly, bypassing the operation-log path that doesn't apply to a side-effecting file write (Recommended). (2) Register `export_scene` as an operation kind in `app.handlers`. (3) Ship as-is with the two tools removed from the registry until fixed, so an agent never discovers this by trying. Impact: high — this is the concrete artifact of "it worked" (1.2). Evidence: live `KeyError` trace; `src/app/app_test.py:66`.

- **["Many readers" has no tools to read with"]** — `INSPECT` and `DETAIL` roles are empty in the real registry, so the collaboration model Gate A 10.1 chose has no read-only path today. (1) Publish `MEASURE_SPECS`/`DETAIL_SPECS` and route read-only queries (e.g. `uv_quality`, already built and unregistered per `src/uv/specs.py`) to `INSPECT` (Recommended). (2) Accept single-writer-only for this pass and say so in HANDOVER. (3) Leave silently empty. Impact: medium — the reader role isn't reachable, but the single-writer path works alone. Evidence: `src/mcp_server/registry.py:35-41`, `registry_test.py`.

- **[Constraints don't survive a reload]** — a saved-and-reloaded scene keeps operations' geometry but loses their constraints, so a moved wall no longer drags its railing after a restart. (1) Extend `persistence.py`'s serialised shape to cover `placements`/`joinery`/`acceptance` now, before more scenes are saved against the incomplete format (Recommended). (2) Document the limitation prominently in the export/save UI so a user knows a reload means re-solving by hand. (3) Leave undocumented. Impact: high — this is ADR-002's stated reason for choosing a parametric document at all. Evidence: `src/scene/persistence.py:67-92`.

- **["What rule it broke" is inconsistent]** — some operation failures name a rule; geometry-helper failures (degenerate paths, zero-length vectors) surface as raw Python exceptions instead. (1) Catch broadly in `adapt()` (not just `TypeError`) and map any unhandled exception to a generic-but-real rule like `operation.internal_error` with the original message as detail (Recommended). (2) Push validation earlier so degenerate geometry is rejected by `validate_params` before it reaches engine code. (3) Leave as-is. Impact: medium-high — the user named this field specifically for reuse in game-design tooling. Evidence: `src/app/handlers.py:152-162`.

- **[A hidden dimension default in the railing tool]** — `post_size`/`baluster_size`/`rail_size` silently default to 5cm/5cm/3cm when omitted, contrary to "the agent supplies every dimension." (1) Make all three required, matching `height`/`post_spacing`/`baluster_gap` (Recommended) — small, mechanical, closes the gap outright. (2) Keep the defaults but surface them in the tool's response as an explicit assumption per call. (3) Leave as-is. Impact: low — narrow blast radius, one operation. Evidence: `src/ops/railing.py:72-74`.

- **[Rigging/organic has zero coverage and no honest write-up]** — A-004 promised a `docs/HANDOVER.md` naming thin areas; it doesn't exist, and the areas in question have no code at all rather than "thin" code. (1) Write `docs/HANDOVER.md` now, naming rigging/organic sculpting as unbuilt and out of realistic reach for this pipeline shape (Recommended) — cheap, and it's the one deliverable A-004 explicitly owes. (2) Attempt a minimal rigging stub before Gate B. (3) Leave unaddressed. Impact: medium. Evidence: absence confirmed repo-wide; `docs/decisions/gate-A.md:31-33`.
