## Blender as an engine (versions, headless, bpy PyPI, API-break history)

**Current version and cadence.** Blender ships on a roughly 4-month cycle. Observed: Blender 5.0 released 2025-11-18, Blender 5.1 released 2026-03-17, Blender 5.2 LTS released 2026-07-14 (blender.org release notes / cookstation.blog summary of blender.org, checked 2026-08-05). Blender 4.5 LTS (2025-07-15) is supported until 2027-07; 5.2 LTS until 2028-07. **This means any design assuming "Blender 4.x" is already one major line behind** — the product should target 5.x, or explicitly pin to 4.5 LTS for stability.

**Headless driving.** `blender --background --python script.py` and `--python-expr "..."` are the standard entry points (observed, multiple sources incl. devtalk.blender.org, checked 2026-08-05). The classic trap, confirmed by Blender's own dev forum: many `bpy.ops` operators are UI-oriented and `poll()`-gate on needing a `window`/`screen`/`area` in `bpy.context` — calling them in `--background` mode throws `RuntimeError: ... poll() failed, context is incorrect` (e.g. `bpy.ops.render.render.poll()` missing `'window'`) (observed, devtalk.blender.org/t/error-bpy-ops-render-render-poll-missing-window-in-context, checked 2026-08-05). The documented mitigation: prefer the data API (`bpy.data`, `bpy.context.scene`, mesh/bmesh APIs) over `bpy.ops` wherever possible in headless scripts, and only use `temp_override()` context managers when an operator is unavoidable (**inferred** as best practice from the same sources, consistent with Blender's own migration guidance below). `bpy.ops.render.opengl()` (Workbench/EEVEE viewport render) needs viewport context and is documented as working with EEVEE/Workbench only, not Cycles (observed, projects.blender.org #116741, checked 2026-08-05); on Linux this additionally needs a virtual display (Xvfb/EGL) since there's no windowing system in headless mode — Windows normally has a GDI/software fallback so this specific trap is Linux-server-specific (**inferred**).

**`bpy` on PyPI.** It exists and is official. Observed (pypi.org/project/bpy, fetched 2026-08-05): current release is **bpy 5.2.0** (2026-07-14), license **GPL-3.0**, and it is **Python-version-locked**: bpy 5.2.0 requires **Python 3.13 exactly** (`Python ==3.13.*`) — no other interpreter version will install it. Wheels exist for Windows x86-64 (338.7 MB), Windows ARM64 (210.6 MB), Linux manylinux_2_28 x86-64 (401.3 MB), macOS 11+ ARM64 (245.1 MB). **This directly collides with the target machine's facts**: the machine has no Python at all, only the Windows Store stub, so `pip install bpy` cannot even be attempted until a real CPython 3.13 is installed — and each future Blender release typically re-locks to a newer Python minor (**inferred** from "each release supports one Python version" language in Blender's own module docs, bioerrorlog.work / developer.blender.org, checked 2026-08-05). `bpy` as a module has no UI/window manager at all (there's no `bpy.context.window` — confirmed by blenderartists.org thread "Blender as a module: no bpy.context.window", checked 2026-08-05) — it is strictly data-API + background-operator territory, a stricter subset of what `--background` mode offers.

**API stability.** There is no formal semver-style stability guarantee. Breaking changes land in most major/minor releases and are documented ad hoc in per-version "Python API" release notes rather than governed by a deprecation policy (**observed pattern**, not a stated policy: developer.blender.org/docs/release_notes/*/python_api, checked 2026-08-05). Confirmed concrete breaks: Blender 2.80 was an explicit API-breaking release; Blender 4.0's Principled BSDF v2 renamed sockets (e.g. `Specular` → `Specular IOR Level`, added `Weight` suffixes to Transmission/Subsurface/Coat/Sheen) — any script or add-on that sets Principled BSDF inputs by name breaks silently or throws `KeyError` across the 3.6→4.0 boundary (observed, blender.org 4.0 shading release notes + blenderartists threads, checked 2026-08-05). Blender 3.2 replaced the old context-override dict pattern (`bpy.ops.object.foo({"object": obj})`) with `bpy.context.temp_override(**kwargs)` as a context manager; the old dict form still works in places but is considered legacy (observed, b3d.interplanety.org "Context overriding in Blender 3.2 and later", checked 2026-08-05). Blender 5.0 (Nov 2025) renamed Grease Pencil APIs to "Annotation" (`bpy.types.GreasePencil` → `bpy.types.Annotation`) (observed, developer.blender.org/docs/release_notes/5.0/python_api, checked 2026-08-05). **Conclusion (inferred): any product pinning to a specific Blender version must budget real engineering time for API-adaptation work on every upgrade** — this is a recurring, not one-time, cost.

## Licensing — the section that can invalidate a design

**Settled facts, both from blender.org's own pages** (observed, blender.org/about/license + the license search-snippet summary of that page and docs.blender.org manual license page, checked 2026-08-05 — note: direct WebFetch of both blender.org/about/license and the docs.blender.org manual page returned HTTP 403 to this agent's fetcher, so these are corroborated via search-engine-cached summaries of the same pages, not a direct page read):
- Blender's source is **GPLv2-or-later**; distributed **binaries** are **GPLv3-or-later**.
- Scripts/add-ons that use Blender's Python API "to define the user interface or develop tools" are treated by the Blender Foundation as **derivative works that must be GPL-compatible if published/distributed**. However, the obligation is triggered by **distribution**, not private use: an add-on kept in-house or sold with source access only to paying customers does not have to be published publicly.
- You **cannot** redistribute a modified Blender binary under a closed license — any redistributed fork must ship under GPL with source.

**Where this gets genuinely contested — flagged, not resolved:**
1. **Importing `bpy` into your own long-running process.** Strict reading: `import bpy` is direct linking/incorporation of GPL code into your process's address space, which under GPLv3 makes your combined program a "work based on" the GPL program — triggering copyleft on your code **if you distribute that combined program**. This is the position implied by Blender's own FAQ language about scripts "using the Blender Python API." A counter-argument circulating in packaging discussions (e.g. nijho.lt/post/gpl, checked 2026-08-05) is that pure aggregation/dynamic-import arguments used for other GPL Python packages don't clearly apply to `bpy`, because `bpy` is not a generic library — it *is* Blender, compiled in. **No court ruling or FSF/Blender Foundation statement definitively settles the "SaaS/subprocess" boundary for bpy specifically; treat this as legally unresolved and get a lawyer before shipping, per Blender's own disclaimer** ("If you want legal advice about the GNU GPL license... please consult a lawyer" — blender.org, checked 2026-08-05).
2. **Running Blender as a separate OS subprocess, talking over stdio/sockets.** This is the position most commentators (packaging blogs, forum threads) treat as safer: subprocess + IPC is commonly analogized to "mere aggregation" (like piping to `grep`), which the GPL FAQ (FSF's, not Blender's) generally does not treat as creating a derivative work of the subprocess. **This is the most defensible path if avoiding GPL contamination of your own codebase matters**, but it is an analogy, not a Blender-Foundation-issued ruling specific to Blender. It also does not free you from GPL obligations on Blender itself — you still must be able to give recipients of *your product* the means to get Blender's own GPL source (trivially satisfied since Blender is public) and must not entangle Blender's binary with technical restrictions (e.g. DRM) that violate GPLv3 anti-tivoization terms if you bundle the Blender binary with your installer.
3. **Shipping a Blender add-on.** Settled: per point above, an add-on that hooks Blender's Python API and is distributed is expected to be GPL-compatible. Selling it with source-on-purchase is allowed; keeping the repo private with no distribution is allowed; distributing it while keeping it proprietary is the position blender.org explicitly warns against.
4. **Hosted web service (SaaS) that runs Blender server-side and only exposes a web UI/API — never distributing Blender or your code to the end user.** Under a strict GPLv3 reading, GPLv3 (unlike AGPLv3) does **not** have a network-use clause — running GPL software on a server and letting users interact with it over the network is **not** "distribution" and does not by itself trigger the obligation to release your orchestration code. This is the one point the community broadly agrees on (GPLv3 has no AGPL-style copyleft-over-network) — **inferred/consensus, not blender.org-specific text, but consistent with the plain language of GPLv3 vs AGPLv3**. If your server-side code never leaves your servers, GPL does not force you to open it, regardless of whether you `import bpy` or subprocess it. The risk is entirely in (1)/(2)-style contamination *of code you do distribute* (e.g., a desktop client, an add-on, a bundled installer), not in the SaaS backend itself.

**Practical decisive takeaway (inferred):** the licensing risk is concentrated in **distributing** software that embeds `bpy`/Blender, not in running it. A pure hosted-SaaS design with a subprocess-isolated Blender backend is the lowest-risk shape; a distributed desktop app or add-on that `import bpy`s directly is the highest-risk shape and should get a lawyer's sign-off before shipping.

## Agent interface (MCP spec, tool-count limits, image cost)

**Spec.** Current protocol version is **2025-11-25** (observed, modelcontextprotocol.io/specification/2025-11-25, fetched 2026-08-05). A Python SDK "v2" rework exists to support a newer **2026-07-28** spec draft per one secondary source (chatforest.com, checked 2026-08-05) — **inferred/unconfirmed against the primary spec site**, which still serves 2025-11-25 as of the fetch date; treat 2026-07-28 as an in-flight/edge revision, not confirmed-stable. **Transports**: `stdio` (subprocess, newline-delimited JSON-RPC over stdin/stdout — default for local servers) and **Streamable HTTP** (single POST endpoint, optionally upgrading to SSE for server-to-client streaming). The older separate HTTP+SSE transport was replaced by Streamable HTTP as of protocol version 2026-03-26 in the numbering scheme some secondary sources use; **SSE-as-a-standalone-transport is deprecated**, SSE-as-an-upgrade-within-Streamable-HTTP is not (observed/consistent across modelcontextprotocol.io/specification/*/basic/transports and multiple 2026 blog summaries, checked 2026-08-05).

**Primitives.** Servers expose **Resources** (data/context), **Prompts** (templated workflows), **Tools** (invocable functions); clients may expose back to servers **Sampling** (server-initiated recursive LLM calls, requiring explicit user consent per the spec's security section), **Roots**, and **Elicitation** (observed, modelcontextprotocol.io/specification/2025-11-25, fetched 2026-08-05). The spec text does not itself state a hard numeric limit on tool count or payload size — those are host/client-implementation limits, not protocol limits (**inferred** from absence of such limits in the fetched spec page).

**Tool-count practical limits — this has real published evidence, not just a vibe.** Observed: an arXiv paper on RAG-MCP reports a baseline tool-selection accuracy of only **13.62%** when an agent is given a large undifferentiated tool set, rising to **43.13%** with retrieval-augmented tool selection (arxiv.org/html/2505.03275v1, checked 2026-08-05). Multiple secondary sources converge on **~10–15 tools** as where accuracy starts degrading, **~30 tools** as where description overlap causes real confusion, and **100+ tools** as a regime where correct tool selection is "virtually guaranteed to fail" for many models (speakeasy.com, tianpan.co/blog/2026-04-19-over-tooled-agent-problem, dev.to/thedailyagent, checked 2026-08-05 — these are blog-level syntheses, not all peer-reviewed, but they cite consistent numbers independently). **Design implication (inferred): a multi-agent/sub-agent architecture that partitions tools per sub-agent role (e.g., "mesh-repair agent" gets 5-8 geometry tools, not all 40) is not a nicety — it is close to load-bearing for tool-call accuracy.**

**Image cost through MCP — a documented footgun.** Observed (GitHub issues on multiple MCP clients incl. anthropics/claude-code#31208, kirodotdev/Kiro#6292, checked 2026-08-05): several MCP clients do **not** convert an `ImageContent` block returned by a tool into a native multimodal image block — they pass the base64 payload through as text, which costs **~15,000–25,000 tokens per image** instead of the ~1,600 tokens the same image would cost as a native image attachment (a **10–20x** token tax). Claude Desktop is reported to hard-cap MCP image resources at **1 MB**. **Design implication: do not rely on MCP's `ImageContent` return path for viewport screenshots without first confirming the specific client/host converts it natively — otherwise a single "look at your work" round-trip can burn 15-25k tokens.**

**Direct image-to-model cost (bypassing MCP, e.g. sending a screenshot straight in a user/tool-result message).** Observed (docs.claude.com/en/docs/build-with-claude/vision, corroborated via search snippets and third-party calculators, checked 2026-08-05): Claude's formula is approximately **tokens ≈ (width_px × height_px) / 750**, with the more precise internal accounting being image patches of 28×28px (`⌈w/28⌉ × ⌈h/28⌉` visual tokens). A 1000×1000px screenshot ≈ **1,334 tokens**; a 2000×2000px screenshot ≈ **~5,300 tokens**. **Design implication: downscaling a "watch it build live" viewport render to ~768–1024px on the long edge before sending it to the judging/orchestrator agent is nearly free in quality and cuts token cost several-fold versus sending full-res renders.**

## Live viewing options

**three.js** (MIT, npm `three`, 0.185.1 latest, ~13.8M downloads/week — observed registry.npmjs.org/three + api.npmjs.org, checked 2026-08-05): the default choice for a custom live-viewer; full control over incremental scene updates (you can patch `BufferGeometry` attributes in place rather than reloading the whole glTF). **Babylon.js**: comparable capability, has an official `@babylonjs/viewer` component and documented WebSocket-driven "push new model to connected clients" patterns (observed, babylonjs.medium.com "Share 3D Models with WebSockets Demo," forum.babylonjs.com threads, checked 2026-08-05) — good if you want a more batteries-included viewer with less custom code. **`<model-viewer>`** (Google web component): simplest to embed, but it is designed around loading a **complete** glTF/GLB per update, not incremental patching — every "agent changed something" event means a full model reload and re-parse, which is fine for occasional checkpoints but not for smooth live-building (**inferred** from model-viewer's load-a-URL design and absence of any partial-update API in search results).

**Streaming approach.** No mainstream production-ready incremental/delta glTF or USD-over-the-wire protocol turned up in this research — glTF has no standard "patch" extension, and USD's composable/layered architecture (which in principle supports delta layers) is a desktop/DCC-interchange feature, not something with an established browser-streaming implementation (**inferred** from absence of hits despite explicit searching). The realistic 2026 options are: (a) full GLB re-export + re-load on each checkpoint (simplest, higher latency, guaranteed-correct), or (b) a custom WebSocket protocol that pushes raw mesh/transform diffs (vertex buffer deltas, node transform changes) which the client applies directly to live three.js/Babylon.js `BufferGeometry` objects (more engineering, lower latency, no drift risk since you're not re-parsing a whole file). **Recommendation-relevant fact, not a recommendation itself**: three.js's own `BufferGeometry`, `Box3`, and `Raycaster` are usable for this without any WASM geometry engine, since they operate on plain typed arrays (**inferred** from three.js's documented API surface).

**Realistic latency.** No dated, sourced benchmark for an end-to-end "agent edits geometry → browser shows it" pipeline was found. **Inferred, not observed**: full-cycle latency is dominated by (1) Blender-side edit + export time (glTF export of a moderate mesh is sub-second to a few seconds depending on scene complexity — no hard number found), (2) file transfer/parse (near-instant for small GLBs, seconds for texture-heavy ones), (3) network hop if hosted remotely. A round-trip in the **1-3 second range per checkpoint** for a modest scene is a plausible ballpark for a full-reload approach; sub-200ms is achievable only with the custom-diff WebSocket approach and only for topology-preserving edits (vertex moves, not remeshing). Treat both numbers as engineering estimates, not measured facts.

## Runtime shape — what can actually be tested on the target machine

Given facts: Node v24.18.0 present, git present; **no Python interpreter** (only the Windows Store `python3.exe` alias stub, which does not run real Python until a package is installed from the Store or a real interpreter is put on PATH); **no Blender**, not on PATH.

- **A Node/TypeScript orchestration layer is testable today, with zero extra installs.** `node:test` (built into Node 24) or `vitest` can run now. This is the only "runs immediately, no setup" option given the machine facts (**inferred directly from the given facts**).
- **A Python orchestration layer (pytest, etc.) cannot be tested until a real Python is installed** — this is a hard blocker today, not a preference. Any test suite that assumes `python -m pytest` will fail out of the box on this machine.
- **Testing geometry code with no Blender present is possible in Node**, using pure-JS/WASM geometry libraries that need no browser and no native Blender:
  - `three` — runs in plain Node for math/geometry (`Vector3`, `Box3`, `BufferGeometry`, `Raycaster`); GPU rendering itself needs a browser or a headless-GL shim, but geometry logic does not (**observed** from three's documented API + `headless-three`/`node-canvas-webgl` ecosystem packages existing specifically to add the rendering piece back for Node, checked 2026-08-05).
  - `manifold-3d` — WASM build, Apache-2.0, confirmed to run under Node (its own CI runs the npm package's tests in Node — observed, github.com/elalish/manifold discussion #754, checked 2026-08-05). Good for boolean ops / solid geometry correctness tests without Blender.
  - `@gltf-transform/core` — MIT, pure Node/TS, ~114k downloads/week (observed 2026-08-05), good for testing glTF I/O and validation without a Blender export step at all.
  - `web-ifc` — MPL-2.0, ships a Node-specific WASM+wrapper pair (`web-ifc-node.wasm`, `web-ifc-api-node.js`) explicitly for non-browser use (observed, github.com/ThatOpen/engine_web-ifc, checked 2026-08-05).
  - `occt-import-js` — LGPL-2.1, Emscripten/WASM wrapper around OpenCASCADE import; usable in Node for parsing STEP/IGES without a native OCCT install (**inferred** from its purpose as a WASM port, not explicitly confirmed Node-only in this pass).
  - `openscad-wasm` — GPL-2.0, WASM port of OpenSCAD; same GPL-contamination question as `bpy` applies if imported into a distributed product (see licence table).
- **Conclusion (inferred, decision-relevant): a pure-Node test suite for geometry logic is achievable on this machine with no Blender and no Python, using `three` + `manifold-3d` + `@gltf-transform/core` as the core testable geometry stack.** Any test that needs to validate actual Blender-produced output (materials round-trip, modifier stack results, etc.) cannot run on this machine until Blender is installed — that class of test should be isolated (e.g., CI-only, or a separate opt-in suite) rather than required for local development.

## Decisions for the user

1. **[Local Blender dependency]** — Does the product require Blender/`bpy` installed on the machine that runs it, or can it be Blender-free? Options: (a) require a full Blender install + subprocess control — most capable, but this machine has **no Blender today**, so local dev/testing is blocked until it's installed; (b) require `bpy` as a Python wheel — blocked doubly, since this machine has **no Python either**, and `bpy` 5.2.0 demands exactly **Python 3.13**; (c) go Blender-free using three.js/manifold-3d/gltf-transform for geometry and skip Blender entirely for anything short of final high-fidelity export. Recommendation: **(c) for the core live-editing loop, with Blender as an optional/CI-only backend for final export or advanced ops** — it's the only option that runs on the target machine as-is. Impact: **high**. Evidence: verified machine facts (given) + bpy PyPI Python-lock (pypi.org, 2026-08-05).

2. **[GPL exposure]** — How do we touch Blender/bpy/PyMeshLab/openscad-wasm without forcing our own code GPL? Options: (a) `import bpy` directly into the product's process and distribute that process — highest contamination risk, contested but risky; (b) subprocess/socket isolation, Blender as an external process — lower risk, aligns with "mere aggregation" reasoning, but unsettled for bpy specifically; (c) hosted SaaS only, Blender server-side, nothing GPL ever distributed to the user — GPLv3 has no network-copyleft clause, so this is the cleanest; (d) avoid GPL geometry engines altogether (manifold, three.js, OCCT/LGPL, Apache-licensed CAD kernels). Recommendation: **(c)+(d) combined** — SaaS delivery plus GPL-free geometry libraries where possible, reserving Blender for an isolated subprocess role. Impact: **high**. Evidence: blender.org licensing FAQ (secondary-sourced, 2026-08-05), GPLv3 vs AGPLv3 network-clause distinction (consensus, unsettled point flagged explicitly above), get a lawyer before shipping any distributed variant.

3. **[Orchestration language]** — Node/TS or Python for the agent-orchestration layer? Options: (a) Node/TS — runs today with zero installs (`node:test`/vitest work immediately) and matches the only proven-testable geometry stack (three/manifold-3d/gltf-transform); (b) Python — natural fit if a real Blender/bpy integration is core, but blocked today on this machine until Python 3.13 is installed, and pytest can't run until then. Recommendation: **Node/TS for orchestration and the testable geometry core**, with Python reserved for an isolated Blender-subprocess worker if/when Blender integration is added. Impact: **high**. Evidence: given machine facts + npm package survey above.

4. **[Rendering engine for agent self-feedback]** — What does the agent look at to judge its own work? Options: (a) Cycles path-trace — best fidelity, "minutes" per frame CPU-only per multiple 2025-2026 benchmarks, unusable for tight iteration loops without a GPU; (b) EEVEE Next — PBR-plausible, seconds not minutes, "3-4x longer" on CPU vs GPU per source; (c) Workbench OpenGL viewport render — sub-second, no lighting/material fidelity; (d) client-side three.js screenshot of the live browser scene — zero Blender dependency, sub-second, matches what the human viewer sees. Recommendation: **(d) as the default judging input, (b)/(c) only if a Blender backend exists and fidelity checks are needed periodically**. Impact: **medium**. Evidence: rendering cost table above (qualitative, dated 2026-08-05); no GPU confirmed present on this machine.

5. **[Tool count per agent]** — How many tools does each sub-agent get? Options: (a) one flat toolset for all agents (simplest to build); (b) role-partitioned toolsets, ~5-10 tools per sub-agent role; (c) retrieval-augmented tool selection (RAG-MCP style) for a large shared catalogue. Recommendation: **(b)**, matching the multi-agent/sub-agent structure already implied by the product brief — published evidence shows accuracy falls off sharply past ~10-15 tools and badly past ~30. Impact: **high**. Evidence: arXiv RAG-MCP paper (13.62% → 43.13% accuracy swing), multiple 2026 blog syntheses converging on the same thresholds (checked 2026-08-05).

6. **[Image return path for agent viewport feedback]** — How does a rendered/screenshotted view get back to the judging model? Options: (a) return it as an MCP tool `ImageContent` block — risk of a client treating it as text and costing 10-20x more tokens (observed GitHub issue reports); (b) attach it as a native image block in the orchestrator's own message construction, bypassing MCP's tool-result path; (c) skip images and describe geometry as data/JSON instead (loses "look at it" fidelity). Recommendation: **(b)** — construct the multimodal message directly rather than routing image bytes through an MCP tool result, until/unless the specific MCP client in use is confirmed to convert `ImageContent` to a native block. Impact: **medium**. Evidence: anthropics/claude-code#31208, kirodotdev/Kiro#6292 (checked 2026-08-05).

7. **[Live-view update strategy]** — Full reload vs incremental diff for the "watch it build live" browser view? Options: (a) full GLB re-export + reload per checkpoint — simplest, correctness-guaranteed, likely 1-3s latency per update; (b) custom WebSocket geometry-diff protocol patching `BufferGeometry` in place — lower latency, more engineering, only handles topology-preserving edits cleanly; (c) wait for a standardized delta format (none found production-ready in this research pass). Recommendation: **(a) first, (b) as a later optimization** once the product's actual edit cadence is known — don't build a custom diff protocol before confirming full-reload latency is actually a problem. Impact: **medium**. Evidence: no incremental glTF/USD-streaming standard found in this pass (absence noted as a finding, not proven non-existent).

8. **[3D-gen API vendor dependency]** — Build geometry natively vs call a hosted 3D-gen API (Meshy/Tripo/Rodin/CSM/Zoo) for parts of the pipeline? Options: (a) no external API, all geometry via own agent + Blender/geometry libraries — no per-call cost, no vendor rate limits, but slower to reach "impressive" results; (b) hybrid, call a hosted API for initial rough geometry then hand off to the agent for refinement — Meshy Pro ($20/mo, 10 concurrent tasks) or Rodin (needs $120/mo Business tier just for API access) are the realistic entry points; (c) full dependency on a hosted API — fastest to a demo, but CSM's Google acquisition (Jan 2026) is a live example of vendor-continuity risk in this exact space. Recommendation: **(a) for the core product** (aligns with "AI models create 3D models live" as the actual value prop, not a wrapper around a vendor API), **(b) only as an optional accelerator behind a flag**. Impact: **medium**. Evidence: pricing table above, CSM acquisition note (sloyd.ai/toosio.com, checked 2026-08-05).

9. **[Blender version to target, if/when Blender is added]** — Options: (a) track latest (5.2 LTS as of 2026-08-05) — gets newest features, LTS support through 2028-07; (b) pin to 4.5 LTS — supported through 2027-07, smaller/older API surface, more third-party add-on compatibility today; (c) track head/daily builds — for cutting-edge features only, unstable. Recommendation: **(a), 5.2 LTS**, and budget explicit migration time at each future LTS jump given the confirmed history of breaking API changes (4.0 Principled BSDF renames, 5.0 Grease Pencil→Annotation rename). Impact: **low** now (Blender isn't required for the core loop per decision 1), **high** later if Blender integration is added. Evidence: blender.org release notes summary, developer.blender.org release-notes Python-API pages (checked 2026-08-05).
